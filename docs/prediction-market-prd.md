# 예측마켓 투표 PRD

문서 버전 2.0 · 2026-09-07 · 대상 코드: `src/market/`, `src/data/voteContent.ts`, `src/pages/VotePage.tsx`

이 문서는 구현된 동작을 그대로 기술한다. 코드에 없는 기능은 "미구현"으로 표시했다.

v2.0 변경: 2026-09-07 요청 스펙 14개를 반영했다. 항목별 구현 여부는 섹션 13에 있다.

---

## 1. 요약

`/vote` 페이지는 단순 투표가 아니라 가격이 계속 움직이는 예측마켓이다. 방문자는 PILL 포인트로 4명의 트레이더 중 누가 1위가 될지에 베팅한다. 호가는 그 트레이더의 마진 잔고가 전체에서 차지하는 비중이다. 그 비중이 곧 확률이다. 30분 카운트다운이 0이 되면 마감하고 자동 정산한다.

백엔드는 없다. 시장 전체가 브라우저 안에서 도는 시뮬레이션이다.

액션 아이템 3개:

1. 로그인과 상금 지급(요청 1번, 14번)을 실제로 할지 결정한다. 하겠다면 백엔드가 선행 조건이다. 클라이언트만으로는 불가능하다. (섹션 10.2, 10.7)
2. 트레이더 4명의 마진 잔고를 실제 대회 데이터로 받을지 결정한다. 지금은 난수 워크다. (섹션 5.1, 10.3)
3. 탈락 기준 2%가 맞는지 확인한다. 지금은 임의로 정한 값이다. (섹션 5.3, 10.9)

## 2. 목표와 비목표

### 목표

- 행사 전 관객이 "누가 이길까"를 돈처럼 걸어보게 한다.
- 실시간으로 숫자가 움직이는 화면을 만든다. 정적인 투표 결과 막대가 아니다.
- 트레이더의 마진 잔고와 그 잔고가 뜻하는 확률을 같은 줄에서 보여준다.
- 서버 없이 동작한다. 배포는 정적 호스팅만 필요하다.

### 비목표

- 실제 금전 거래. PILL은 현금 가치가 없다.
- 사용자 간 실제 유동성 매칭. 상대방은 시뮬레이션이다.
- 지정가 주문, 오더북. 시장가만 지원한다.
- 베팅 물량을 확률에 반영하는 가중치 알고리즘. 요청 12번에서 명시적으로 제외됐다.

로그인과 리더보드 상금은 요청됐지만 현재 아키텍처에서 구현 불가다. 비목표가 아니라 차단된 목표다. 섹션 13을 본다.

## 3. 핵심 개념

| 개념 | 정의 | 코드 위치 |
| --- | --- | --- |
| PILL | 게임 내 포인트. 시작 잔고 1,000 PILL. | `voteContent.ts:STARTING_BALANCE` |
| 계약(contract) | 베팅 1단위. 적중하면 100 PILL 지급, 틀리면 0. | `voteContent.ts:CONTRACT_PAYOUT` |
| 마진 잔고 | 트레이더의 대회 잔고(USDT). 호가의 원천. | `marketEngine.ts:OPEN_MARGINS` |
| YES | 해당 트레이더가 1위가 된다에 베팅. | `marketEngine.ts:quote` |
| NO | 해당 트레이더가 1위가 못 된다에 베팅. 가격은 `100 − YES가격`. | `marketEngine.ts:quote` |
| 가격 | 0~100 사이 정수. 그대로 확률(%)로 읽는다. | `marketEngine.ts:chanceOf` |
| 탈락 | 마진 비중 2% 미만. 잔고 0, YES 0, NO 100으로 고정. | `marketEngine.ts:isEliminated` |

계약 하나의 손익 구조는 단순하다. 34 PILL에 YES를 사면 적중 시 100 PILL을 받는다. 순이익 66 PILL. 틀리면 34 PILL 전액 손실.

## 4. 시장 규칙

### 4.1 트레이더와 시가

| 트레이더 | 시작 마진 잔고 | 시가 | 색상 |
| --- | --- | --- | --- |
| Variational | 34,000 USDT | 34 | `#caff5d` |
| Lighter | 28,000 USDT | 28 | `#5dd0ff` |
| Aster | 25,000 USDT | 25 | `#ff9f5d` |
| Extended | 13,000 USDT | 13 | `#c98dff` |

마진 합계 100,000 USDT, 가격 합계 100. 가격은 마진 비중에서 계산되므로 이 합은 항상 유지된다. (섹션 5.2)

### 4.2 가격 = 확률 = 마진 비중

표시되는 `34%`는 Variational YES의 호가 34 PILL과 같은 수다. 그리고 34,000 / 100,000 과도 같은 수다. 세 숫자가 같은 값이다. 별도 확률 계산은 없다.

### 4.3 정산

- 마감 시각 `closeAt`에 도달한 첫 틱에서 정산한다.
- 승자는 **그 순간 가격이 가장 높은 트레이더**다. (`winnerOf`)
- 탈락자는 가격이 0이므로 승자가 될 수 없다.
- 동점 시 배열 순서상 앞선 트레이더가 이긴다. Variational → Lighter → Aster → Extended.
- 지급: 승자 YES 보유분 × 100 PILL. 그리고 승자가 아닌 트레이더의 NO 보유분 × 100 PILL.
- 정산 후 주문은 전부 거부된다. (`applyTrade`의 `if (state.settlement)`)
- 정산은 1회만 실행된다. 이미 `settlement`가 있으면 시간만 갱신한다.

### 4.4 카운트다운

- 기본 1,800초 = 30분. (요청 2번)
- 최초 방문 시각 + 1,800초를 `closeAt`으로 저장한다. 재방문해도 카운트다운은 이어진다.
- **행사 실제 시각과 연동되어 있지 않다.** 사용자마다 마감 시각이 다르다.

## 5. 가격 엔진 사양

파일: `src/market/marketEngine.ts`

### 5.1 틱

- 주기 1,000ms. `setInterval` 1개. (`useMarket.ts:TICK_INTERVAL`)
- 매 틱마다 트레이더별 마진 잔고에 균등분포 `±1.4%`를 곱한다. (`MARGIN_DRIFT`)
- 가격을 직접 흔들지 않는다. 마진 잔고가 움직이고 가격은 따라온다.
- 시드는 매 틱 `Math.random()`으로 새로 뽑는다. 결정론적이지 않다.

### 5.2 가격 = 마진 비중 (RFQ 체결)

```
가격_i   = 마진_i / 마진합계 × 100
YES 호가 = round(가격_i)
NO  호가 = 100 − YES 호가
```

- 요청 11번 그대로다. 매수·매도가는 해당 포지션 잔고의 전체 비중값이다.
- 4개 가격의 합은 항상 정확히 100이다. 정규화가 공식 안에 들어있다.
- v1의 리밸런스 계수(0.35)와 `[2, 96]` 클램프는 삭제했다. 필요 없어졌다.
- 한 트레이더의 마진이 늘면 나머지 셋의 확률이 자동으로 줄어든다.

### 5.3 탈락

- 매 틱 드리프트 직후, 마진 비중이 2% 미만인 트레이더의 마진을 0으로 만든다. (`ELIMINATION_SHARE`)
- 0이 된 마진은 되살아나지 않는다. 드리프트는 `margin > 0`일 때만 적용된다.
- 결과: YES 호가 0, NO 호가 100. 요청 14번 그대로다. 별도 분기 없이 5.2 공식에서 나온다.
- 탈락자의 몫은 생존자에게 비중대로 재분배된다.
- 탈락자에 대한 **신규 매수는 거부**한다. 보유분 청산은 허용한다. (`applyTrade`)
- 화면에서는 해당 행이 흐려지고 `탈락` 배지가 붙는다. YES/NO 버튼은 비활성화된다.

### 5.4 체결 임팩트: 없음

RFQ 호가는 트레이더의 마진 잔고에서 나온다. 참가자의 베팅은 마진 잔고를 바꾸지 않는다. 따라서 내 주문이 내 호가를 밀어 올리지 않는다. v1의 `TRADE_IMPACT`는 삭제했다.

판단: RFQ에서는 이게 맞다. 외부 기준가로 호가하는 방식이기 때문이다.
이 판단이 틀리는 조건: 베팅 물량 자체를 확률에 반영하고 싶을 때. 그때는 마진 비중과 베팅 비중을 가중 평균해야 한다. 요청 12번 "가중치 알고리즘"이 정확히 그 작업이고, 이번 범위에서 제외됐다.

### 5.5 봇 체결

- 매 틱 34% 확률로 가짜 체결 1건 생성. (`FILL_CHANCE`)
- 트레이더 랜덤, YES/NO 각 50%, 수량 5~144계약, 방향은 **항상 매수**.
- 봇 체결은 가격에 영향을 주지 않는다. 테이프 표시와 거래량 누적에만 쓰인다.
- 최근 12건만 유지한다. (`FILL_LIMIT`)

### 5.6 초기 히스토리

- 페이지 로드 시 과거 6시간을 즉석에서 생성한다. 180포인트 × 120초 간격.
- 고정 시드 `20260906` 사용. 차트의 과거 구간은 항상 같은 모양이다.
- 이후 실시간 포인트가 뒤에 붙는다. 최대 3,600개 유지.

## 6. 주문 사양

파일: `src/market/useMarket.ts:applyTrade`, `src/components/OrderTicket.tsx`

### 6.1 주문 종류

시장가만 지원한다. 매수/매도 × YES/NO = 4가지 조합. (요청 5번, 6번)

### 6.2 검증 규칙

주문은 아래 중 하나라도 걸리면 **조용히 무시된다**. 상태가 그대로 반환된다.

| 조건 | 결과 |
| --- | --- |
| 정산 완료됨 | 거부 |
| 수량 ≤ 0 | 거부 |
| 탈락한 트레이더에 대한 신규 매수 | 거부 |
| 매수인데 `가격 × 수량 > 잔고` | 거부 |
| 매도인데 해당 포지션 미보유 | 거부 |
| 매도인데 보유 수량 < 주문 수량 | 거부 |

UI는 같은 조건을 미리 계산해 제출 버튼을 비활성화하고 안내 문구를 띄운다. 리듀서 거부는 최종 방어선이다.

### 6.3 주문 티켓 UI

- 기본 수량 10계약. 시작 잔고 1,000 PILL 기준으로 한 번에 소진되지 않는 크기다.
- 증감 버튼: −1 / +1, 그리고 +1 / +10 / +100 / MAX.
- MAX는 매수 시 `floor(잔고 / 가격)`, 매도 시 보유 수량.
- 요약 3줄: 가격, 지불액(또는 수령액), 적중 시 수령액(또는 잔여 계약).
- 체결 후 `role="status"` 영역에 체결 문구를 출력한다.

### 6.4 포지션 (요청 7번)

- `(트레이더, YES/NO)` 조합당 1행으로 합산한다.
- 평단은 `누적비용 / 수량`.
- 부분 매도 시 비용을 비례 차감한다. 전량 매도 시 행을 제거한다.
- 미실현 손익 = `수량 × 현재호가 − 누적비용`.
- 체결 이력은 테이프에서 `data-mine="true"`로 구분된다. 최근 12건까지만 남는다. 전체 체결 로그는 미구현이다.

## 7. 상태 저장

키: `perpdex.market.v2` (localStorage)

저장하는 것:

```json
{ "closeAt": 0, "balance": 0, "holdings": [], "settlement": null }
```

저장하지 않는 것: 마진 잔고, 가격, 히스토리, 체결 테이프, 거래량.

즉, 새로고침하면 **마진 잔고와 가격은 시가(34/28/25/13)로 리셋되지만 잔고와 포지션은 유지된다.** 탈락도 리셋된다.

판단: 이건 버그가 아니라 트레이드오프다. 가격까지 저장하면 오래 자리를 비운 사용자가 정지된 차트를 보게 된다.
이 판단이 틀리는 조건: 30분 세션에서 탈락이 실제로 발생하는 경우. 탈락한 트레이더가 새로고침 한 번에 부활하면 규칙이 무너진다. 마진 잔고를 저장 대상에 넣어야 한다.

v1 키에서 v2로 올린 이유: 시작 잔고가 10,000에서 1,000으로 바뀌었다. 기존 방문자의 저장된 10,000 PILL을 그대로 두면 새 규칙과 섞인다.

## 10. 알려진 한계

정직하게 적는다. 아래는 전부 의도된 제약이거나 미해결 문제다.

### 10.1 시장이 공유되지 않는다

각 브라우저가 자기만의 시장을 돈다. A가 Variational을 크게 사도 B의 화면에는 아무 일도 일어나지 않는다. 테이프에 뜨는 상대 거래는 전부 봇이다.

해결하려면 백엔드가 필요하다. 현재 아키텍처로는 우회 불가능하다.

### 10.2 잔고를 조작할 수 있다 — 상금과 연결하면 즉시 차단 이슈

localStorage에 평문으로 저장된다. 개발자 도구에서 `balance`를 1,000,000으로 바꿀 수 있다. 코드 수정도 필요 없다. 값만 고치면 된다.

v1에서는 "경품과 연결하지 않는 한 문제되지 않는다"고 적었다. 요청 14번이 그 조건을 깼다. 상위 50명에게 USDT를 주고 1등에게 100달러를 준다면, 지금 코드로는 순위표 전체가 자기신고 값이다. 서버 검증 없이는 배포 불가다.

### 10.3 승자가 실제 결과와 무관하다

마감 시점 가격이 가장 높은 트레이더가 이긴다. 그 가격은 마진 잔고의 난수 워크에서 나온다. 행사에서 실제로 무슨 일이 일어났는지와 연결점이 없다.

마진 잔고 모델은 실제 데이터를 꽂을 자리를 만들어 두긴 했다. `stepMargins`를 실거래소 API 폴링으로 교체하면 나머지는 그대로 동작한다. 그 API가 없으면 여전히 난수다.

### 10.4 확률 합 — 해결됨

v1에서는 합계가 94~106 사이를 오갔다. v2는 마진 비중으로 가격을 정의하므로 항상 정확히 100이다. (섹션 5.2)

### 10.5 탭이 닫혀 있으면 정산되지 않는다

정산은 틱 안에서 일어난다. 브라우저가 꺼져 있으면 틱이 없다. 재방문 시 첫 틱에서 정산된다. 이때 승자는 재방문 시점의 가격(시가에서 다시 출발한 값)으로 결정된다.

30분 세션에서는 v1의 3시간 24분보다 이 문제가 커진다. 자리를 비울 확률 대비 세션이 짧다.

### 10.6 정산 후에도 포지션이 남는다

지급은 정상적으로 1회만 되지만 포지션 목록은 비워지지 않는다. 마감된 계약이 계속 표시된다.

### 10.7 로그인이 없다 (요청 1번 미구현)

인증 주체가 없다. 따라서 "내 포인트"는 브라우저에 묶여 있다. 시크릿 창을 열면 1,000 PILL을 다시 받는다. 기기를 바꾸면 기록이 사라진다.

### 10.8 상금 지급 경로가 없다 (요청 14번 미구현)

리더보드는 화면에만 있다. 지갑 주소 수집, 순위 확정, USDT 전송 중 어느 것도 코드에 없다.

### 10.9 탈락 기준 2%는 임의값이다

`ELIMINATION_SHARE = 0.02`는 근거 없이 정한 숫자다. 드리프트 ±1.4%에서 시가 13%인 Extended가 2%까지 내려가려면 상당한 시간이 필요하다. 30분 세션에서 탈락이 거의 발생하지 않을 수 있다.

이 값이 틀리는 조건: 행사에서 탈락 장면을 실제로 보여주고 싶을 때. 그때는 기준을 올리거나(예: 8%) 드리프트를 키워야 한다. 실제 대회 규칙이 있다면 그 규칙을 그대로 쓰는 게 맞다.

## 11. 반론

이 설계에 대한 가장 강한 반박:

**시뮬레이션 시장은 예측 시장이 아니다.** 진짜 예측 시장의 가치는 여러 사람의 돈이 모여 집단 지성이 가격에 반영되는 데 있다. 여기서는 가격이 난수다. 관객이 이 사실을 눈치채는 순간 화면 전체가 장식으로 보인다. 특히 크립토 행사 관객은 예측 시장을 잘 안다. 속이기 어려운 집단이다.

이 반박이 성립하지 않는 조건: 목적이 "예측"이 아니라 "행사 전 대기 시간에 손을 움직이게 하는 것"일 때. 그 경우 난수 시장으로 충분하고, 백엔드 비용 0이 오히려 정답이다.

v2에서 반박이 한 단계 세졌다. 요청 14번의 USDT 상금은 "장식"과 양립하지 않는다. 돈이 걸리는 순간 관객은 숫자의 출처를 묻는다.
